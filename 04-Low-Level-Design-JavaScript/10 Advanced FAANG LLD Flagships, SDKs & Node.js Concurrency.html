Problem 16: Design Notification System (Extensibility & OCP)

LLD MACHINE CODING ARCHITECTURE Problem 16: Design Notification System (Extensibility & OCP)
Low-Level Architecture: Encapsulates domain business invariants within rich entity models, managed by decoupled service orchestrators adhering to Gang of Four (GoF) structural and behavioral design patterns.
ExtensibilityNotification SystemOCP Strategy

Extensible Notification Gateway dispatching Email, SMS, Push, WhatsApp, and Slack messages with provider fallback strategies.

JavaScript — Extensible Notification System
class NotificationProvider {
    send(recipient, message) { throw new Error("Abstract method"); }
}

class EmailNotificationProvider extends NotificationProvider {
    send(recipient, message) {
        console.log(`📧 [EMAIL SENT] to ${recipient}: ${message}`);
        return true;
    }
}

class SMSNotificationProvider extends NotificationProvider {
    send(recipient, message) {
        console.log(`📱 [SMS SENT] to ${recipient}: ${message}`);
        return true;
    }
}

class NotificationService {
    #providers = new Map();

    registerProvider(channel, provider) {
        this.#providers.set(channel, provider);
    }

    notify(channel, recipient, message) {
        const provider = this.#providers.get(channel);
        if (!provider) throw new Error(`Unsupported channel: ${channel}`);
        return provider.send(recipient, message);
    }
}

const ns = new NotificationService();
ns.registerProvider("EMAIL", new EmailNotificationProvider());
ns.registerProvider("SMS", new SMSNotificationProvider());

ns.notify("EMAIL", "alice@example.com", "Your order has shipped!");
ns.notify("SMS", "+15550199", "Your OTP is 482910");

ReliabilityPayment SystemIdempotent Webhooks

Payment Processing Engine featuring status state machines (`INITIATED -> CAPTURED`), idempotent webhooks, and reconciliation.

JavaScript — Idempotent Payment Processor
class PaymentGatewayEngine {
    #processedEvents = new Set();

    processWebhook(event) {
        if (this.#processedEvents.has(event.eventId)) {
            console.log(`[DUPLICATE IGNORED] Webhook event ${event.eventId} already handled.`);
            return { status: "ALREADY_PROCESSED" };
        }

        this.#processedEvents.add(event.eventId);
        console.log(`💳 [PAYMENT SUCCESS] Charge ${event.chargeId} confirmed! Amount: $${event.amount}`);
        return { status: "SUCCESS" };
    }
}

const pg = new PaymentGatewayEngine();
pg.processWebhook({ eventId: "EVT_99", chargeId: "CHG_1", amount: 49.99 });
pg.processWebhook({ eventId: "EVT_99", chargeId: "CHG_1", amount: 49.99 });

Client-side Feature Flag SDK evaluating user percentage rollouts, targeting rules, and caching flags locally with background sync.

JavaScript — Feature Flag SDK Implementation
class FeatureFlagSDK {
    #flags = new Map();

    setFlag(flagKey, isEnabled, rolloutPercentage = 100) {
        this.#flags.set(flagKey, { isEnabled, rolloutPercentage });
    }

    isFeatureEnabled(flagKey, userId) {
        const flag = this.#flags.get(flagKey);
        if (!flag || !flag.isEnabled) return false;

        // Simple hash-based percentage rollout calculation
        let hash = 0;
        for (let i = 0; i < userId.length; i++) hash = (hash << 5) - hash + userId.charCodeAt(i);
        const userBucket = Math.abs(hash) % 100;

        return userBucket < flag.rolloutPercentage;
    }
}

const ff = new FeatureFlagSDK();
ff.setFlag("new_checkout_ui", true, 50); // 50% rollout
console.log("User 1 Has Feature:", ff.isFeatureEnabled("new_checkout_ui", "user_101"));
